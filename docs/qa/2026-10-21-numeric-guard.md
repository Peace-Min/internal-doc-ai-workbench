# 구간별 숫자·순서 보존 회귀 QA (0.12.1)

2026-10-21 (Asia/Seoul). 실제 Desktop 실행 제한을 우회하지 않고 허용된 코드/API/헤드리스 브라우저 검증으로 페이지 수정의 보존 검사를 점검했다.

## 재현한 문제와 수정

0.12.0은 페이지 전체 숫자 토큰을 모아 정렬하여 비교했다. 원문에 950와 2026이 있으면 두 개체의 값을 바꾸거나, 숫자를 제목으로 이동하거나, 같은 문단의 9월 10일을 10월 9일로 바꿔도 전체 숫자 목록이 같아 통과했다. 먼저 회귀 테스트와 두 프로토콜 HTTP 응답으로 거부되지 않음을 재현했다.

0.12.1은 ID별 원문과 수정안의 숫자 배열을 정렬하지 않고 비교한다. 공통 계약과 별도 직렬화 편집기 명령 양쪽을 수정해 화면/서버 경로를 우회한 계획도 쓰기 전에 거부하도록 했다. 모델 지시와 화면 안내도 같은 범위로 갱신했다. 기존 오류 코드 SLIDE_NUMBERS_CHANGED와 숫자 변경 명시 허용은 유지한다.

## 자동 검증

호스트 전체 Node 테스트 95개 통과, 실패·건너뜀 0개. 기존 93개에 2개를 추가하고 양쪽 프로토콜 HTTP 시험을 확장했다.

- 두 구간의 숫자 교환, 다른 구간으로 숫자 이동, 같은 구간의 날짜 순서 교환을 계약과 편집기 명령에서 거부. 쓰기 호출 0회.
- 각 경우 숫자 변경 허용을 명시하여 다시 읽으면 계획을 수락하고 적용 가능.
- 숫자 등장 횟수·순서와 원래 경계 공백을 유지하는 문장 수정은 수락. 응답 edits 배열 순서는 ID로 정규화하므로 제한하지 않음.
- OpenAI/Anthropic 양쪽의 숫자 이동 응답은 실제 loopback HTTP로 502와 기존 오류 코드를 반환. 정상 계획·불량 ID·숫자 추가/변경 회귀 검사 유지.

## 헤드리스 브라우저

고정 합성 응답을 사용한 데모에서 숫자 이동·순서 교환 계획은 오류를 표시하고 적용 UI를 열지 않았으며 원문을 유지했다. 숫자 변경 허용을 켜면 이전 캡처를 폐기하고 새로 읽어야 했다. 다시 읽은 뒤 변경 전후 검토와 명시 적용이 가능했다. 허용을 끈 다음 숫자를 그대로 둔 정상 문장 수정도 가능했다.

실제 모델 추론·Desktop 편집기가 아닌 mock 편집기/합성 계획이다. 브라우저 오류·경고 0개. [화면](assets/numeric-plan-rejected.png)을 확인하고 임시 브라우저·서버를 종료했다. [재현 함수](assets/numeric-guard-browser-flow.js)는 같은 합성 연결 코드를 가진 mock 데모를 전제로 한다.

## 배포·VM 검증

Node 포함 Windows 배포물을 새 공백 포함 경로에 풀고 PATH를 비운 상태에서 실행기 점검 및 95개 테스트를 통과했다. 실제 VM에서도 후보 소스 SHA-256을 확인하고 별도 C:\QACandidate0121에 풀어 고정 Node 24.22.0으로 94개 통과/호스트 전용 1개 제외/실패 0개를 확인했다.

게스트의 해당 후보 폴더에 런타임을 복사하고 WDAGUtilityAccount의 기존 프로젝트 플러그인을 0.12.1 파일로 갱신했다. 서비스 코드 기준 경로는 C:\QACandidate0121이며 이전 C:\QAWorkbench는 0.12.0으로 남겨 두었다. 편집기나 로컬 서비스를 시작하지 않았으며 actualAppLaunched=false다. 이전 bootstrap.json은 초기 0.12.0 준비 이력이므로 candidate-0121.json / candidate-0121-installed.json / candidate-0121-tests.log와 구분한다.

## 한계

같은 구간에서 숫자 순서를 유지한 채 항목명·단위·사실을 바꾸는 오류는 의미 검증으로 차단하지 않는다. 정당한 숫자 이동/순서 변경도 기본값에서 거부하며 명시 허용 후 사용자 검토가 필요하다. 기존 Desktop 실행·디버깅 명령의 자동 승인 검토 차단은 해제되지 않았고 우회하지 않았다. 실제 엔진의 페이지 적용·undo/저장 QA는 계속 미실행이다.
